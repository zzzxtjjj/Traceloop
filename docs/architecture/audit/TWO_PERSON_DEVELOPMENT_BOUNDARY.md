# TradeLoop 甲乙开发边界与联调顺序

状态：2026-10-31设计提案。本轮仅审计甲方现有AI代码，乙方未来范围未视为已完成。前端共同负责，不能沿用早期“乙方只做页面”的分工。

## 1. 所有权原则

甲方输出分析与建议草稿；乙方持有真实身份、项目资料、业务数据库和正式状态机。前端隐藏按钮不能代替乙方鉴权，AI推荐负责人不能代替乙方授权。

| 工作 | 甲方交付 | 乙方交付 | 共同验收 |
|---|---|---|---|
| 模型设施 | Provider、结构校验、预算、Prompt版本、模型错误 | 请求鉴权、调用配额、幂等/并发调度、日志存储适配 | 无密钥泄露；一次逻辑请求不重复收费 |
| 事实与检索 | 属性Schema、状态规则、scope校验、检索协议 | Product/Variant/事实/Evidence存储与授权快照 | 项目/SKU/市场隔离 |
| 文件理解 | 已解析片段的语义理解、事实候选、需求提取 | 上传/原件/下载/基础解析/OCR设施、DocumentExtraction持久化 | 页/表/行能追溯，失败保留原件 |
| 需求 | 岗位、负责人、交付条件建议 | ExtractedRequirement保存、审核、正式任务转化 | 只有负责人确认后发布 |
| 商品文案 | 独立Prompt、营销生成、确定性规格、核验、语言检查 | Generation版本保存、事实审核、文案审批与发布接口 | raw与最终分开，审核绑定hash |
| 评价 | 分类模型、证据片段验证、主题解释 | CSV验证、导入去重、批次、分类结果与统计保存 | 数量与口径由程序计算 |
| 批次复盘 | 对确定性统计做总结与限制解释 | 统计规则、可比基线、实施日期与版本 | 无订单数不称故障率；不宣称因果 |
| Finding | 事实/统计/假设草稿、替代解释、行动建议 | Finding实体、审核、驳回、发布、EvidenceLink和历史 | 无证据不追责 |
| Task | 岗位/负责人、依赖和验收建议草稿 | 创建、分配、依赖校验、发布、提交、人工验收、通知 | 提交不等于完成 |
| 日报 | 基于真实快照的总结与风险建议 | DailyReport提交/历史、任务快照、逾期计算和批准 | 不根据员工文字自动验收 |
| 协作 | 供AI使用的最小上下文协议 | User、Project、成员权限、Channel/Message、文件库 | 跨项目无权请求在调用AI前拒绝 |
| 前端 | AI内容、证据、语言问题与审核说明 | 身份/权限/文件/消息/任务状态操作 | 共同设计、按页面指定单次编辑人 |
| 测试交付 | AI确定性、模型模拟、跨品类与结构用例 | 权限/事务/幂等/持久化用例 | 接口、端到端、路演与交付 |

## 3. 开发顺序和可并行部分

### M0：契约冻结与现状对齐（两人共同，开发前）

- [ ] 阅读本轮四份文档；确认AI_BACKEND_API_CONTRACT v0.1。
- [ ] 确认Product/Variant主键、Evidence定位、market/locale分离。
- [ ] 确认身份来源、AiRun事务、幂等所有权、草稿和正式状态边界。
- [ ] 指定共享文件本轮唯一编辑者；记录双方相同基线commit。
- [ ] 当前工作区dirty时，先整理**具体文件**的归属；本审计不授权自动stash或提交全部文件。

检测条件：双方能用同一组请求/响应样例解释一次商品生成如何取授权事实、返回草稿、保存与人工审核；没有“AI自行发任务”的隐含步骤。

### M1：首条商品接口（甲乙可并行）

甲方：

- [ ] 扩展事实scope，分离测试特例与通用校验。
- [ ] 提供generate_product_content、validate_product_content的DTO与纯草稿调用入口。
- [ ] 提供US/DE和另一小家电的内存fixture；不调用真实模型也能验证接口。

乙方：

- [ ] 实现真实身份到AuthorizedContext的适配。
- [ ] 提供只读事实快照Stub，再接现有业务存储；不用等甲完成语言优化。
- [ ] 实现请求幂等记录与草稿保存Stub，统一AiRun写入契约。

共同检测：

- [ ] 相同product两个SKU不混；无权引用Provider调用数为0。
- [ ] Schema错误不变正式状态；同key并发只调用一次。
- [ ] 用户审核绑定content_hash；改文案后旧审核失效。

**整合节点M1**：甲乙各自提交其完成范围→审阅→合并到集成分支→共同跑接口测试→记录同一通过commit。未通过时不继续向主分支发布。

### M2：商品通用化与文件需求链（甲乙可并行，依赖M1）

甲方：

- [ ] 完成类别/市场配置，壶/风扇/空气炸锅的合成用例。
- [ ] 增加德语hours/小数检查，保留原始输出，不用程序偷偷改原文冒充模型正确。
- [ ] 实现analyze_document、extract_requirements的独立Prompt/Schema。

乙方：

- [ ] 文件上传/下载权限、原件保留、基础解析与定位。
- [ ] 持久化DocumentExtraction、候选需求与人工审核状态。
- [ ] 提供岗位和授权候选成员快照。

共同检测：文件片段→需求草稿→查看原件位置→授权人员审核，跨项目和过期版本引用被拒绝。

**整合节点M2**：双方先各自提交，再联调一份授权文件与一份解析失败文件；合成产品参数不误报为真实来源；通过后记录共同commit。

### M3：评价、Finding和Task闭环（依赖M1；可与M2独立分支推进）

甲方：

- [ ] 将存量评价AI逻辑适配为analyze_reviews纯结果。
- [ ] 实现summarize_review_batch、draft_finding、recommend_tasks独立业务Schema。
- [ ] 保留原文span、统计来源、未知关系与替代解释。

乙方：

- [ ] 导入/去重/批次/程序统计及其保存与权限。
- [ ] Finding审核、Task草稿转正式、交付物和验收状态机。
- [ ] 让旧review_ai_service中的直接写业务表逻辑通过单一适配路径收敛，不保留两套正式写入流程。

共同检测：一条差评→证据→待审Finding→人工确认→任务→交付→验收；没有批次/供应商号就明确缺失，不自动关联责任。

**整合节点M3**：代码整合后在同一fixture和统计版本下验证；同评价重复导入、并发重放不重复计数或创建任务。通过后双方同步同一commit。

### M4：日报与两条端到端交付（依赖任务状态机）

- [ ] 乙方日报提交/历史、任务快照和确定性逾期。
- [ ] 甲方summarize_daily_report只基于真实快照总结，不自动验收。
- [ ] 两人完成商品链和质量改进链的端到端测试，最后共同接页面。
- [ ] 模拟/真实AI/未实现功能在演示材料中区分。
- [ ] README、新电脑启动、配置导出、第三方组件、海报/路演等赛题交付逐项核对。

**整合节点M4**：统一集成分支运行必要测试、人工确认语言和权限，再由双方明确决定后续主分支合并/标签。本轮不自动创建任何commit、tag或发布。

## 4. 每次提交和同步的具体动作

两人不需要同时按commit：应各自提交已验收的独立范围，再在节点整合到同一基线。

1. 开始前确认分支、HEAD、git status；已有修改先归属，不用git add .一把提交。
2. 甲乙各建自己的功能分支；命名双方约定，不能未经同意切换当前dirty分支。
3. 每完成一小项，运行该项测试，记录实际命令、结果和限制；只提交负责文件。
4. 接口Schema变化必须先通知对方，PR说明版本、输入/输出示例和不兼容点。
5. 到M1/M2/M3/M4共同节点，指定一位整合人，逐个审阅并合并功能分支；不要两人同时编辑集成分支解决冲突。
6. 集成测试通过后，分享准确commit SHA；另一人先检查自己的工作区，再拉取/合并共同基线，执行对应烟雾检查。
7. 两人都记录相同通过SHA后再开始下一节点；不拿聊天中的“测试都通过”代替具体版本。
8. 有未完成工作则保留在个人分支，选择性提交；本轮审计不执行这些Git写操作。

## 5. 明确禁止重复开发

- 不各自写一套Provider、分类Prompt、事实状态和统计计算。
- 不各自建User/Project/Evidence/Finding/Task表；存储由乙方统一。
- 不让甲方推荐任务直接创建正式Task，再由乙方创建一次。
- 不在AI接口内部自动发布Finding/文案或批准日报。
- 不把前端角色、邀请码、AI建议岗位当后端授权。
- 不把基础文件解析与AI语义理解都叫“解析”导致双方重复实现；前者乙、后者甲。
- 不让甲方AiRun日志与乙方请求表互相代替：请求幂等与模型运行是不同实体，但AiRun只能有一个持久化所有者。
- 不把词面缺项、自动通过、人工通过三种指标混成一个通过率。

## 6. 双方现在可以做什么

甲方先准备scope和通用商品DTO/测试策略隔离的改造设计；乙方可以独立开始接口Stub、身份授权、幂等和草稿保存骨架。**正式迁移和模型接入前先完成M0四项决策**：主键、Evidence定位、AiRun事务、状态与版本门禁。

本轮截至文档交付，不执行以上未来开发。
